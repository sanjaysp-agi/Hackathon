# Intelligent Workflow Manager — Architecture & Build Plan
**Hack_2026_008 · LSMV PV Workflow Control Tower**

> Turns LSMV workflow data from *"what happened"* (QBE/LSBI reports) into a live
> control tower that answers: **What is happening? Why? What happens next? What should I do?**

---

## 1. Guiding principle (read this first)

This is a **regulated pharmacovigilance** context. The single most important
architectural decision:

> **Numbers are computed deterministically. Language, reasoning, and
> recommendations are generated by the LLM — grounded in those numbers.**

- The **Metrics & Risk Engine** (plain Python, no LLM) computes every score,
  count, deadline, and threshold. These are **reproducible, testable, auditable**.
- The **Agentic AI layer** never invents a number. It *reads* engine output via
  tools, then **explains, predicts, and recommends** in natural language with
  citations back to the underlying data.

This split is what makes AC #6 (Explainability), #10 (Governance), and audit
readiness real instead of a demo trick. An auditor can re-run the math; the AI
only ever adds the narrative on top.

## 4. Data layer

### 4.1 Normalized model (derived from the problem's field list)

```
Case
  case_id, case_type, seriousness (serious/non-serious), complexity (low/med/high),
  reporting_due_date, reporting_status, country/region, product,
  created_at, workflow_status (open/in-progress/on-hold/closed)

Activity                       (a case moves through many activities = workflow steps)
  activity_id, case_id, activity_name (e.g. Data Entry, Medical Review, QC,
  Submission), activity_status (not-started/in-progress/complete/overdue),
  activity_due_date, assigned_to (user), team, start_ts, end_ts

ReassignmentEvent
  activity_id, from_user, to_user, ts, reason?

User / Team
  user_id, name, team, role, capacity (nominal activities/day or hours/day)

HistoricalTurnaround          (benchmarks for prediction & "stuck" detection)
  activity_name, case_type, complexity → p50, p80, p95 duration (hours)
```

**Derived at ingest** (computed, cached): `aging_days` per activity,
`time_in_current_activity`, `days_to_reg_deadline`, `reassignment_count`.

### 4.2 "Now"
The dataset is a snapshot. We treat `max(timestamp in data)` (or a configurable
`AS_OF` date) as **"now"** so deadlines/aging are meaningful without live clocks.
Lets the demo be deterministic and reproducible.

### 4.3 Ingestion
`ingest.py`: load the LSMV extract → validate/coerce types → build the normalized
tables → precompute derived fields → persist to SQLite (`lsmv.db`). Re-runnable.
**Plug the real dataset in here.** Until it arrives, a `synthesize.py` produces a
schema-compatible dataset so the whole stack is buildable/testable today.

## 5. Metrics & Risk Engine (deterministic core)

Pure functions over the normalized model. Each returns both the **value** and the
**supporting evidence** (the rows/fields behind it) so the AI and the UI can cite it.

### 5.1 Workflow Health score (AC #1)
Weighted composite, 0–100, mapped to Green/Amber/Red:

```
health = 100
  − w1 · (% activities overdue)
  − w2 · (% cases with reg-deadline risk)
  − w3 · (bottleneck severity index)
  − w4 · (workload imbalance index)
  − w5 · (% stuck cases)
```
Weights are a named config (`weights.yaml`) → tunable, inspectable, defensible.
Return per-component contribution so the UI shows *why* the score is what it is.

### 5.2 Regulatory risk (AC #2) — pre-overdue, deterministic
For each case with a `reporting_due_date`:
```
days_left = reporting_due_date − now
work_left_est = Σ p80(remaining activities for this case_type/complexity)
risk = HIGH   if work_left_est > days_left  (can't finish in time)
       MEDIUM if work_left_est > 0.7 · days_left
       LOW    otherwise
```
Flags risk **before** anything is technically overdue — the core differentiator.

### 5.3 Predictive SLA risk (AC #3) — historical performance
Per in-flight activity, compare elapsed time against historical distribution:
```
if time_in_activity > p80(activity_name, case_type, complexity): at risk
expected_completion = start_ts + p50(...)   # projected finish
```
MVP uses **percentile benchmarks** (robust, explainable). Optional stretch: a
small gradient-boosted model for breach probability — only if time allows and
**only as an input the engine exposes with its features**, never a black box.

### 5.4 Bottleneck detection (AC #4)
Group in-flight + recent activities by `activity_name` / `team` / `stage`:
```
bottleneck_score(stage) = median_wait_now / p50_historical_wait
                        × (queue_depth / throughput_last_period)
```
High score + growing queue = bottleneck (e.g. "Medical Review"). Return the
contributing cases so the manager can drill in.

### 5.5 Workload intelligence (AC #5)
Per user/team: `utilization = assigned_open_work / capacity`.
Flag >100% (overloaded) and <~60% (slack) → surfaces imbalance and the
reassign opportunity. Capacity comes from the User table (or a default).

### 5.6 Aging / stuck cases
`stuck` = `time_in_current_activity > p95(historical)` for that activity type.
"3 cases in the same activity far longer than norm" comes straight from here.

> Every engine function returns `{value, status, evidence[], explanation_inputs}`.
> The AI consumes `explanation_inputs`; the UI renders `evidence`.

## 6. Agentic AI layer (Claude via Bedrock)

### 6.1 Model & access
- **Claude on AWS Bedrock** (we have `AWS_BEARER_TOKEN_BEDROCK`).
- Reasoning/NBA/chat: **Claude Opus 4.8** (`us.anthropic.claude-opus-4-8`) or
  **Sonnet** for faster/cheaper turns. Make it a config switch.
- Access via `anthropic[bedrock]` SDK (`AnthropicBedrock`) or `boto3` bedrock-runtime.

### 6.2 Tool-calling design (this is the "agent")
The agent does **not** get raw SQL or free rein. It gets a **typed toolbox** that
wraps the engine — so every answer is grounded and auditable:

```
Tools exposed to Claude:
  get_workflow_health()                       → health score + components
  list_regulatory_risk(level?, team?)         → cases at reg-deadline risk + why
  list_sla_risk(activity?, team?)             → predicted breaches + evidence
  get_bottlenecks()                           → ranked stages/teams + contributors
  get_workload(team?)                         → utilization per user/team
  list_stuck_cases()                          → aging/stuck activities
  get_case(case_id)                           → full drill-down for one case
  recommend_next_best_action(case_id|team)    → engine-scored action candidates
```

Flow for a manager question ("Which cases will miss their deadline?"):
`Claude → list_regulatory_risk(level=HIGH) → gets rows+evidence →
composes grounded NL answer with case IDs and the reason for each`.

This satisfies AC #9 (ask questions) and keeps AC #6/#10 intact — the agent can
only speak about data the tools returned, and we log the tool calls.

### 6.3 Next Best Action (AC #7)
Two-stage, keeps humans in control:
1. **Engine** proposes candidate actions with scores (rule-based): e.g.
   `prioritize` (reg risk high + days_left low), `reassign` (owner >100% & peer has
   slack), `escalate` (stuck > p95 & serious), `monitor` (medium risk, trending ok).
2. **Claude** turns the top candidate into a clear recommendation *with rationale
   and the data behind it* — and the UI makes the manager **Accept / Dismiss /
   Modify**. Nothing auto-executes. Every decision is logged.

### 6.4 Guardrails
- System prompt: *"Only use values returned by tools. Never state a number not
  present in tool output. Always cite case/activity IDs. If data is missing, say so."*
- No tool that mutates case data in MVP (read-only control tower) → safe demo.
- Tool outputs capped/paginated so prompts stay bounded.

## 7. Governance & audit (AC #10)

- **Audit log** (`audit` table): every AI recommendation and chat answer records
  `timestamp, manager, question/trigger, tools_called, data_snapshot_id,
  recommendation, human_decision (accept/dismiss/modify)`.
- **Explainability by construction**: because numbers come from the engine, every
  claim links to `evidence[]` rows the UI can display ("show me the data").
- **Human-in-the-loop**: AI recommends, never acts. Decisions are explicit + logged.
- **Reproducibility**: snapshot id + versioned `weights.yaml` means any score can
  be recomputed and defended later.

## 8. API surface (FastAPI)

```
GET  /api/health                      → workflow health score + components
GET  /api/risk/regulatory?level=      → reg-deadline risk list
GET  /api/risk/sla                     → predicted SLA breaches
GET  /api/bottlenecks                  → ranked bottlenecks + contributors
GET  /api/workload?team=               → utilization per user/team
GET  /api/cases?filter=                → case list (sortable by risk/aging)
GET  /api/cases/{id}                   → full case drill-down (activities, history)
GET  /api/cases/{id}/next-best-action  → scored NBA candidates
POST /api/chat        {message, ctx}   → agentic answer (SSE stream of tokens)
POST /api/decisions   {rec_id, action} → log human decision on a recommendation
GET  /api/audit                        → audit trail
```

All GET endpoints are thin wrappers over engine functions → fast, cacheable,
testable without the LLM.
